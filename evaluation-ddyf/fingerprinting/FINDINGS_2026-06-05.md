# Live-TCP fingerprinting — findings (2026-06-05)

Honest summary of the OpenSSL + WolfSSL live-TCP fingerprinting investigation, for
deciding how to frame RQ5. Numbers are reproducible from the scripts here
(see `REPRODUCE.md`).

## TL;DR

| | offline (display-execute) | **live-TCP (real server)** |
|---|---|---|
| **OpenSSL** (61 ver) | 61 clusters but **ASAN-poisoned**: ERROR-driven, only **4** real | **53 clusters**, reproducible matrix, but **fragile**: 45/53 separated by ≤2 traces → robust ~13–35 |
| **WolfSSL** (24/26 ver) | 20 clusters, **clean** (0% ERROR), well-separated (median 25) | **14 clusters**, **31% EMPTY**, fragile (9/14 separated by 1 trace) |

The honest headline: **the *discrimination* exists in the signatures, but robust
*live identification* over TCP is noise-limited** — for both stacks, most
version-clusters differ on only 1–2 probe traces, which is at the per-connection
live jitter floor.

## What is solid

1. **The live matrices reproduce at the cell level.** Re-probing a version's full
   129-trace (OpenSSL) column matches the stored matrix to ~0–1/30 cells, across
   two independent runs and both 200 ms/500 ms read timeouts. So the clustering is
   a stable property, not a fluke.
2. **Method correctness.** OpenSSL display-execute is invalid (the PUTs are
   ASAN-instrumented and abort non-deterministically on the malformed probes →
   `ERROR`; with ERROR as a wildcard only 4 clusters remain). The valid signal is
   the wire response from the real **non-ASAN** `vendor/<v>/bin/openssl` server,
   captured over TCP with most-complete + majority sampling. WolfSSL display-execute
   *is* clean (0% ERROR) — its 21-cluster paper result stands as an offline result.

## Why live identification is fragile

- The decision-tree walk and nearest-cluster matching both fail end-to-end (4–7/61
  for OpenSSL) **not because the matrix is wrong**, but because the clusters are
  separated by only 1–2 traces. A single per-connection signature flip (≈3% of
  cells over TCP) on a distinguishing trace moves a version to a neighbouring
  cluster. The tree is worst-hit: its decision probes are *the* most-discriminating
  (hence noisiest) traces.
- OpenSSL is **data-limited**: the campaign yielded only 129 deterministic
  TCP-observable diff traces, so per-cluster separation is intrinsically tiny.
- WolfSSL live adds a second effect: the stock example server returns **no
  parseable response for ~31%** of probes (it closes/errors where the in-process
  PUT, following the trace's server role, "responded"). So display-execute
  over-states what a real generic server reveals, and the live trace-selection
  (picked from display-execute separations) transfers poorly.

## Why OpenSSL display-execute can't be salvaged cheaply

The 40% `ERROR` is *genuine in-process non-determinism* (5 display-execute runs
disagree), not just ASAN leak-report pollution: setting `ASAN_OPTIONS=detect_leaks=0`
removes the leak noise but the matrix is still 40.3% ERROR. The ERROR *pattern* is
reproducible (so the 61 "clusters" are stable and well-separated, 56/61 ≥5 traces
apart) but the signal is "this version's instrumented PUT fails non-deterministically
on this malformed probe" — and crucially the in-process PUT fails on **40%** of
probes while the **real non-ASAN server fails on only ~1%**. So display-execute does
*not* reflect what a remote server reveals; it is an artifact of the ASAN-instrumented
in-process PUT. (`candidates_ossl_disp2/` = leaks-off rebuild, for the record.)

### UPDATE — the "non-ASAN rebuild" is moot (investigated 2026-06-05)

The OpenSSL PUTs are **already non-ASAN**. `nm vendor/openssl3XX/lib/libssl.a` has
**0 `__asan` symbols** — openssl is compiled with **sancov only** (the non-asan
preset `[openssl340]`, not `[openssl340-asan]`). ASAN was a carry-over mental model:
the `-asan` presets exist for the *fuzzing campaigns* (ASAN catches the memory bugs a
fuzzer hunts), but fingerprinting correctly uses the non-asan presets. The libasan /
LeakSanitizer output is only the **asan runtime library** linked to provide the
*sancov* coverage runtime; the openssl code itself is not memory-checked.

So the 40% display-execute `ERROR` is **not** ASAN — it is either sancov
instrumentation or genuine openssl non-determinism on malformed input. Testing that
would need a *non-sancov* openssl rebuild (multi-hour, recompiles openssl, uncertain).

But it would not help anyway: **display-execute discrimination is an in-process
artifact, not wire-observable.** The in-process PUT fails on 40% of probes while the
real server fails on ~1% (live EMPTY); even a perfectly deterministic display-execute
would fingerprint by *which probes crash the in-process PUT*, which a remote observer
never sees.

### CORRECTION (from sonnet's auditor Q&A, HANDOFF/AUDITOR_QA.md)

OpenSSL is **NOT intrinsically hard to fingerprint** — the fragility is a *sampling
artifact*. The matrix uses **129 of 111,436** objective traces the campaigns actually
produced (AGY triage sampled ~100 per experiment); **~111k traces were never mined.**
The 61-cluster model was **never validated end-to-end** (lab_validate never run;
3-version spot-checks failed 0/3) — it was matrix-distinctness only, inflated by the
22% EMPTY truncation cells. Real high-separation signals exist (confirmed
library-level HelloRetryRequest split 3.1.x vs 3.3.x: HRR vs HRR+Alert(IllegalParameter);
ServerHello-content and alert-type probes separating ~900-1000 pairs each), but the
129-sample lacks *redundant* traces for the closest pairs.

**The lever is mining the existing 111k pool** (no new fuzzing needed): select traces
that separate the fragile pairs with redundancy (≥K distinct real-TLS signatures per
pair) — the same redundancy-preserving selection that made WolfSSL robust — rebuild the
live matrix on that targeted subset, recluster, re-measure separation.

## Recommended framing for the paper

- **WolfSSL stays as is (offline, 21 clusters)** — clean, reproducible, already in
  the paper. Add a sentence that a live prober reproduces the well-separated
  clusters but fine-grained pairs need repeated probing.
- **OpenSSL**: do **not** report the old contaminated "61". Two honest options:
  1. Report the live-TCP result as **"53 reproducible signature clusters; robust
     live identification of ~13–35 well-separated clusters"**, framed as a
     data-limited lower bound (more fuzzing → more separation).
  2. **Best for a clean, WolfSSL-comparable result: rebuild the OpenSSL PUTs
     non-ASAN (sancov only) and use display-execute** — without ASAN the PUTs no
     longer abort, so display-execute should give clean, well-separated clusters
     like WolfSSL. This is the recommended next step; it was out of scope here
     (a multi-hour 61-version rebuild).
