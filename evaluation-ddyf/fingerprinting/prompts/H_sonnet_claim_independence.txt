## Background
Our pipeline fingerprints wolfssl server versions by replaying probe traces and hashing the
server's observable response (see evaluation-ddyf/fingerprinting/{_canon.py, signatures.py,
build_tree.py, candidates/{tree.json,clusters.json,signatures.csv,manifest.csv}}). Headline
result so far: 26 versions -> 21 clusters, depth-3 tree, 10 probes.

CONCERN: a remote fingerprint must be reproducible from the BLACK-BOX wire channel only.
But two things may smuggle in PUT-internal information that a real remote server never
exposes over TCP:
  1. `_canon.py:run_display` executes with `-c -p`; the `-p` post-execution terms feed
     `extra_knowledges`, which IS part of the signature (_canon.py:132-136). Some of those
     may be decryptions that rely on secrets the in-process PUT exposes via claims.
  2. `seed --fingerprinting` keeps `seed_client_attacker_auth`, which needs
     `client_authentication_transcript_extraction` (a CLAIM/transcript channel). Probes
     descended from it may reference terms a black-box server can't supply.
Also: the `AllowClaim` patch is applied only to 5.5.0+ (see discover.sh) — if it perturbs
on-the-wire behavior at all, that unevenness is a confound in the clustering.

## What to determine

## Method (tiered — cheapest decisive test first)
1. WIRE-ONLY recompute (conservative lower bound). Recompute every signature with
   `display-execute` using `-k` only (NO `-c`, NO `-p`), re-cluster, rebuild the tree.
   - If the partition is still 21 clusters and the appendix self-check still holds
     (A0=5.0.0 alone, A1={5.1.0,5.1.1}, B=5.2.0), then discrimination needs no claims at
     all -> DONE, fully safe. Report it.
   - If it MERGES clusters (fewer than 21), some discrimination came from `-p`/claims.
     Go to step 2 for the affected probes/pairs only.
2. GOLD-STANDARD live test (for the affected probes). The `tcp -j --json` flag now exists.
   For each affected probe and a couple of affected versions, stand up that version as a
   real TLS server on a socket, replay the probe with `tlspuffin tcp --json --host H --port P`,
   and compare the live signature to the offline `signatures.csv` entry. A real client
   derives its own keys, so decryptions it can do legitimately are fine; only mismatches
   reveal true claim dependence. Keep probes whose live signature matches; drop the rest.
3. AllowClaim wire-neutrality. Build one 5.5.0+ version WITH and WITHOUT `AllowClaim`,
   compute its signatures over the tree probes, and confirm they are identical. If not,
   `AllowClaim` is not wire-neutral and the clustering is confounded — report loudly.
4. Rebuild `clusters.json` / `tree.json` restricted to the claim-independent probe set.
